# M9 — Email-code auth, providers, settings

## Login

- Replace passwords with six-digit email codes. Verify the code to sign in or create an account; keep refresh-cookie sessions.
- SMTP env: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`.
- `make start` reads/writes only `apps/api/.env`; never create a root `.env`. The existing `.gitignore` entry for `apps/api/.env` protects these secrets. Generate and preserve `AUTH_SECRET`; prompt for missing SMTP values.
- Keep code hashes, expiry, and attempt counts in an in-memory map. Codes are single-use, short-lived, rate-limited, and invalidated on process restart. No password fields, routes, or UI.

## Account creation

- Login and account creation share one flow and one screen: type an email, receive a pin, confirm, and land in the app. The backend only checks whether the account exists; if not, it creates it on pin success.

## Providers and errors

- Show Model and Search together on one Settings page so neither is missed. Explain that Model generates and validates answers, while Search retrieves web pages as evidence; model setup is required to ask, search is optional.
- On first Workspace load, make one provider-status request. If model fields are absent, show a centered dismissible prompt whose primary action opens Settings to Providers. The prompt is dismissible; users can continue without configuring a key.
- Missing/unusable model config or a configured provider error settles the normal node as `failed` with a descriptive error. Preserve the node and partial output; offer Retry and Settings. Retry only after the user fixes the key. No extra provider error state.
- Unconfigured search is skipped. Empty search results continue without sources; a configured search provider error fails the node.
- Verify replacement keys before saving. Never return saved keys to the browser.

## Settings and user schema

- Keep Account and Appearance/Asking separate; put Model and Search together on one provider settings page, with clear purpose text and required/optional status.
- Replace `users.search` and `users.settings` JSON with columns. Model and search each have base URL, model name, and encrypted key; omit verification timestamps.
- Store theme, reading size, linked-presets flag, and selection/follow-up preset arrays on `users`. Presets are ordered `{label, instruction}` entries: label is the visible button text, instruction is its ask modifier, and the array determines order. “Selection” and “follow-up” describe which UI offers each set. Do not create a `user_presets` table or a general settings JSON blob.
- Store no login-code table. Update the base schema and fixtures; no incremental migration file is needed.

## E2E

- Cover email-code login, account creation, expiry, resend/attempt limits, and generic responses. Screenshot the login and account creation page. 
- Screenshot the initial Workspace with no model, the dismissible Settings prompt, and a failed ask with a Settings path.
- Screenshot provider failure in an existing burrow, partial output, Retry, failed replacement preserving the old key, and recovery after a valid replacement plus explicit Retry.
- Cover absent search, empty results, and configured search failure.

**Exit:** password auth is removed; email-code login and SMTP setup work; provider failures use normal node failure; Settings and user schema are simplified and covered by E2E.
