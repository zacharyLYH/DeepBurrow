# M6 — Auth and user data isolation

> Shipped. Auth tables live in `001_init.sql`; this pre-release DB does not keep incremental migrations. The demo account exists only in test fixtures; the API never seeds it.

M6 moves DeepBurrow from the single demo account to password-based accounts. Every API read and write must be scoped to the authenticated user. This closes the existing cross-user data exposure risk before adding more integrations.

**Exit test:** create two accounts; each can sign in, change its password, use its own burrow and settings, and cannot read, mutate, stream, cancel, restore, or infer the other account's data by changing IDs. Expired access cookies refresh successfully; invalid, revoked, and expired refresh credentials do not. No authenticated route falls back to the demo user.

## Scope

- Email + password sign-up and sign-in; no password reset flow in this milestone.
- Change password in Settings, requiring the current password and a valid new password. Revoke existing refresh sessions after a password change.
- JWT access and refresh authentication in Secure, HttpOnly, SameSite=Lax cookies. Keep access lifetime short (15 minutes); refresh lifetime is configurable and materially longer (for example, 30 days).
- Rotate refresh credentials on use, persist only a digest/revocation record, and detect reuse. Provide logout that revokes the current session. The refresh cookie is scoped to `/api/auth/refresh` and is only issued/rotated by the auth routes.
- Derive user identity exclusively from verified server-side credentials. The browser never supplies an authoritative user ID.
- Scope every burrow, node, settings, and user-owned API operation by the authenticated user. IDs are selectors, never authorization.
- Give each new user a private initial burrow. Migrate existing demo data to an explicit account or documented local-only fixture; never make it a shared fallback account.
- Add a Sign in / Sign up surface and account controls (email, change password, sign out) to Settings. Keep appearance and asking preferences user-specific and server-persisted.
- Add schema migration and indexes needed for password credentials and refresh sessions. Preserve current user data during migration.

## Credential storage decision

Passwords must be stored as a one-way, deliberately expensive password hash (Argon2id preferred; scrypt/bcrypt only if deployment constraints require it), with per-password random salts and parameters that can be upgraded. **Do not AES-encrypt passwords.** AES is reversible encryption, not password hashing. An environment secret may be used as a separately named pepper if operationally manageable, but it is not a replacement for the password hash. Keep JWT signing keys separate from any encryption key, load secrets from environment configuration, and fail startup when required production secrets are absent.

## Auth and cookie contract

| Concern | Contract |
|---|---|
| Access | Signed JWT, 15-minute expiry, HttpOnly + Secure + SameSite=Lax cookie; validate signature, issuer, audience, expiry, and subject |
| Refresh | Rotating signed refresh JWT with session identifier and expiry; HttpOnly + Secure + SameSite=Lax; cookie Path is `/api/auth/refresh`; persist session state for revocation and reuse detection |
| Cookie issuance | Sign-in issues both cookies. Refresh endpoint rotates and reissues both. Refresh cookie is only set by these auth routes; clear it on logout using matching attributes |
| Password change | Verify current password, hash new password, revoke all refresh sessions, require sign-in again |
| CSRF | SameSite=Lax plus Origin/Host validation on state-changing requests; never enable permissive credentialed CORS |
| Errors | Do not reveal whether an email exists on sign-in; rate-limit sign-in and sign-up; never log passwords, cookies, or tokens |

JWTs are bearer credentials even when held in cookies. Keep claims minimal (`sub`, `iss`, `aud`, `iat`, `exp`, and refresh session identifier where needed); do not put private profile or secret data in them.

## User isolation audit

All data access helpers take an authenticated `userId` or resolve through an owned burrow. Queries must include ownership in SQL rather than fetch by ID and authorize later. For nodes, verify ownership through the node's burrow in the same operation. Apply this to:

- `GET /burrows/:id`, viewport updates, node reads and patches, branch delete/restore.
- `/ask`, retry, parent lookup, node creation, stream attach/replay, cancel, and run bookkeeping. A parent, retry target, or stream node must belong to the same user.
- `/settings` reads and writes, and password/account routes.
- Any future export or search endpoint.

Return the same not-found response for missing and non-owned resources. SSE authorization occurs before opening the stream. Run registries and cancellation must not let one user affect another user's run. Remove `DEMO_BURROW` routing and first-row user/settings lookups.

## Acceptance checklist

- [x] Two users receive separate initial burrows and separate settings.
- [x] Missing/invalid credentials cannot use any private endpoint; no route accepts a caller-supplied owner ID.
- [x] Cross-user IDs cannot be used to read or alter burrows, nodes, settings, runs, or stream state.
- [x] Refresh cookie has the required attributes and path; access cookie is short-lived; refresh rotates and can be revoked.
- [x] Logout and password change invalidate refresh sessions; password change requires current-password proof.
- [x] Passwords use a one-way password hash; no password is AES-encrypted or stored in plaintext.
- [x] The browser sends credentials automatically and handles an access refresh without replaying a mutation unsafely.
- [x] Production startup fails clearly when signing secrets are missing or weak; secrets never enter frontend bundles or logs.
- [x] Sign-in and sign-up have basic abuse controls and generic credential errors.
